# k6 stress test — baseline result (2026-09-28)

Run once as a baseline for the portfolio, not tracked over time (`test-plan.md` §3.6). Both runs
target **local dev only** (`D:\Project\Qicau`, `npm run dev`, `PORT=3001`, isolated from the
dev server already running on port 3000), with Gemini stubbed via
`environments/stubs/gemini-fetch-mock.cjs` — never the real Gemini endpoint or production.

## `parse-ramp.js` — brief ramp, 1→20 VUs

`MOCK_SCENARIO=high` (every model call succeeds immediately).

```
k6 run -e BASE_URL=http://localhost:3001 performance/parse-ramp.js
```

| Metric | Result |
|---|---|
| Total requests | 1,663 |
| Failed requests | 0 (0.00%) |
| `http_req_duration` avg / p90 / p95 / max | 1.43ms / 1.96ms / 2.37ms / 6.46ms |
| Threshold `p(95)<3000` | ✅ pass (2.37ms) |
| Threshold `http_req_failed rate<0.05` | ✅ pass (0.00%) |
| Peak throughput | ~31.6 req/s at 20 VUs |

All requests returned 200 with a well-formed `result` field. Latency is dominated by
server/network overhead, not model latency, since the mock resolves instantly — this baseline
demonstrates the server handles concurrent load cleanly, not real Gemini response times.

## `parse-edge-case.js` — fallback chain forced under load

`MOCK_SCENARIO=primary-fail-fallback-success`, `MOCK_FAIL_COUNT=1` — every single request forces
at least one failed primary-model attempt before the fallback succeeds (API-07 exercised on
every request, not just occasionally).

```
k6 run -e BASE_URL=http://localhost:3001 performance/parse-edge-case.js
```

| Metric | Result |
|---|---|
| Total requests | 900 |
| Failed requests | 0 (0.00%) |
| `http_req_duration` avg / p90 / p95 / max | 1.44ms / 2.06ms / 2.26ms / 24.57ms |
| Threshold `p(95)<6000` | ✅ pass (2.26ms) |
| Threshold `http_req_failed rate<0.05` | ✅ pass (0.00%) |
| Peak throughput | ~29.9 req/s at 15 constant VUs |

Every request still resolved to 200 despite every attempt requiring at least one fallback hop —
the fallback chain (API-07) holds up under concurrent load with no errors or timeouts, at least
against the mocked upstream (this does not measure real Gemini latency/availability under load,
which is explicitly out of scope per `test-plan.md` §2.2).

## Notes
- No failures, timeouts, or dropped connections in either run — nothing to file as a bug from
  this pass.
- This is a small-scale demonstration of the practice (per `performance/README.md`), not a
  capacity-planning exercise — the server under test is a local Express dev instance, not
  production infrastructure.
